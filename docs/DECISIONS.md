## D-0010 — OSM road graph: explicit direction/access rules over OSMnx defaults (2026-11-04)
**Status:** implemented in Issue #6 (pending review). **Decision:** OSMnx 2.1.1 builds and simplifies the graph, but direction and motor-car access are classified from raw tags in `gis/src/circuitforge_gis/rules.py` (OSMnx would treat `oneway=reversible/alternating` and unknown values as two-way, and `custom_filter` does not apply its drive access exclusions). Ways with an uncertain direction keep only their drawn-order edge and are non-routable; conditional, mode/direction-specific and unrecognised restrictions are flagged for review and non-routable; untagged access/oneway follow the OSM default with the basis recorded. The full graph is kept with weak (all edges) and strong (routable edges) component ids; boundary-crossing segments keep their first outside OSM node. Lengths use the AOI's `length_crs` (EPSG:6680 for Sapporo), refused when the AOI falls outside the CRS area of use; GeoJSON is EPSG:4326. Simplification keeps parallel edges (their end nodes are forced endpoints) and is verified one-to-one by per-edge `edge_uid`. Data is fetched with the Issue #4 pinned query (identical element hash). Service roads are excluded in the MVP profile, with a `drive-with-service` profile prepared. **Limitations:** turn restrictions not modelled; route generation (#10) must use only `aoi_status="inside"` routable edges and recompute SCCs on that subgraph; 22 trunk/primary/secondary ways are two-way only by OSM default and need checking before #10. Evidence: [evidence/issue-6/README.md](evidence/issue-6/README.md).

## D-0011 — Course exchange format v0.1.0: ordered OSM segments in a GeoJSON Feature (2026-11-04)
**Status:** implemented in Issue #7 (pending review). **Decision:** a course is one GeoJSON Feature whose ordered `segments` (`edge_uid = way_id:segment_index:f|r`, shared with the road graph) are the source of truth; geometry and length are derived and re-validated against the graph rebuilt from the pinned OSM snapshot. Manual authoring uses via points with shortest-path completion on routable, inside-AOI edges (ties broken by the lexicographically smallest `edge_uid` sequence) or an explicit segment list; validation rebuilds the graph from the trusted AOI config and rejects courses whose `aoi`/`length_crs` disagree with it, and checks U-turns at the circuit closing join; this is an authoring aid, not course generation (#10+). `edge_uid` in the Issue #6 graph was redefined from construction order to this OSM-based form (audit results unchanged). **Alternatives:** free-form LineString (cannot be checked against one-ways/access); node-id lists (ambiguous for parallel segments). **Data/licence:** only synthetic samples are committed; Sapporo demo courses are generated locally from a committed recipe because publishing OSM-derived files awaits the #12 licence policy. Spec: [ARCHITECTURE.md](ARCHITECTURE.md#course-contract-decided-v010-issue-7).

## D-0012 — 3D scene: PLATEAU-Terrain without Cesium ion; buildings only on terrain (2026-11-04)
**Status:** implemented in Issue #8 (pending review). **Decision:** use PLATEAU-Terrain (quantized-mesh, `https://tile.plateauview.mlit.go.jp/terrain`, ellipsoidal heights) via `CesiumTerrainProvider.fromUrl`, and PLATEAU building 3D Tiles (LOD2 without texture per ward, else LOD1). Both are described in `config/scene.<aoi>.json` with a snapshot (SHA-256, version, retrieval time) so a provider change only needs a new config and a re-verification. Buildings are displayed only when the terrain loaded and passed a metadata/height probe; otherwise the viewer shows map and course only. **Alternatives:** A) PLATEAU terrain via Cesium ion (token, ion terms); B) GSI DEM tiles + geoid (custom terrain code). C was chosen after a technical check (CORS, loading, display, 81/81 buildings within ±2 m) and confirmed in implementation (88/88 within the provisional ±2 m). **Risks:** both services are trial services; terrain data licence unconfirmed (#12). Evidence: [evidence/issue-8/README.md](evidence/issue-8/README.md).

## D-0013 — Vehicle animation: CC0 model, centre-line path, separate terrain sampling (2026-11-04)
**Status:** implemented in Issue #9 (pending review). **Decision:** use Kenney Car Kit 3.1 `race.glb` (CC0 1.0, generic open-wheel car, shipped unmodified with its texture; provenance and SHA-256 in `config/vehicle.json`). The vehicle position is interpolated on the course polyline itself (never off the centre line); only its heading is smoothed (8 m chord window). Terrain heights are sampled separately (2 m, chosen after measuring: cost is dominated by ~9 terrain tile requests, while 5 m interpolation deviated up to 0.42 m). Ground offset 0 m (model origin at tyre contact). Cameras: chase, onboard-like (ahead of the nose, as the model has no cockpit), aerial, free. Display speed 40 km/h × playback multiplier, labelled as non-physical. **Alternatives:** Khronos ToyCar (CC0, 5.4 MB, material extensions), CesiumMilkTruck (CC BY 4.0, contains Cesium logo), primitive placeholder. **Results:** 300/300 grounding samples within the provisional ±0.3 m; heading deviation 0° away from vertices, no reversals. Evidence: [evidence/issue-9/README.md](evidence/issue-9/README.md).
